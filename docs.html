Read this first

Every lab below starts from a fresh Ubuntu machine and ends with a cleanup block, so you can do any one of them alone. Your manual's terminal screenshots are from Ubuntu lab PCs.

Docker install used in every lab (the same docker.io package your Lab 1 output shows):

sudo apt-get update
sudo apt-get install -y docker.io
sudo systemctl enable --now docker
sudo usermod -aG docker $USER
newgrp docker
docker --version
  • newgrp docker applies the docker group in the current terminal, so you don't need sudo before every command. If you still get permission denied ... docker.sock, log out and back in, or prefix commands with sudo.
  • Windows/macOS: install Docker Desktop, start it, and wait until it says the engine is running. The commands are identical.
  • If apt can't find a package, use curl -fsSL https://get.docker.com | sudo sh instead. It installs Docker Engine and the Compose plugin. Use it in place of docker.io, not on top of it.

Typos fixed from the manual. The PDF lost its underscores: Flask( name ) is Flask(__name__), if name == " main " is if __name__ == "__main__":, depends on is depends_on, and docker-compose. yml is docker-compose.yml. Everything below is corrected.

How to use it. Each lab runs Step 0 (install), numbered steps, expected result, then cleanup. File blocks use cat > file <<'EOF', so you can paste a whole block into the terminal; typing the same text in nano gives the same file. Run a lab's cleanup before starting the next one, or ports 5000, 5001, 5432 and 8080 will clash.

Lab 1 — Docker installation and container lifecycle

Goal: install Docker, pull alpine and nginx, run a container, list running and stopped containers, then stop, start and remove them.

Step 0 — Install Docker (fresh machine)

sudo apt-get update
sudo apt-get install -y docker.io
sudo systemctl enable --now docker
sudo usermod -aG docker $USER
newgrp docker

Step 1 — Verify the installation

docker version
docker info

Expected: client and server details and engine information, no error.

Step 2 — Pull the official images

docker pull alpine
docker pull nginx

Step 3 — Verify the downloaded images

docker images

Expected: both alpine and nginx are listed.

Step 4 — Run nginx as a detached container

docker run -d --name lab-nginx -p 8080:80 nginx
curl http://localhost:8080

Expected: a container ID is printed, and curl (or a browser at http://localhost:8080) shows the nginx welcome page.

Step 5 — Run alpine once (extra, not in the manual)

Alpine exits right after its command, which gives you a stopped container to see in docker ps -a.

docker run --name lab-alpine alpine echo "Alpine is running"

Step 6 — List running containers

docker ps

Expected: only lab-nginx.

Step 7 — List all containers, including stopped ones

docker ps -a

Expected: lab-nginx (Up) and lab-alpine (Exited (0)).

Step 8 — Stop the container

docker stop lab-nginx

Step 9 — Start the stopped container again

docker start lab-nginx
docker ps

Step 10 — Stop and remove the containers

docker stop lab-nginx
docker rm lab-nginx
docker rm lab-alpine
docker ps -a

Expected: an empty list. A running container can't be removed until it is stopped (or removed with docker rm -f).

Lab 2 — Build and run an app with a Dockerfile

Goal: package a Flask app on port 5000 with a Dockerfile, build it as myapp:v1, tag it 1.0, run it with port mapping and reach it with curl. You don't need Python on the host; Flask is installed inside the image.

Step 0 — Install Docker (fresh machine)

sudo apt-get update
sudo apt-get install -y docker.io
sudo systemctl enable --now docker
sudo usermod -aG docker $USER
newgrp docker
docker --version

Step 1 — Create the project folder and app.py

mkdir -p ~/lab2 && cd ~/lab2
cat > app.py <<'EOF'
from flask import Flask

app = Flask(__name__)

@app.route("/")
def home():
    return "Hello from the CCAI Docker Lab!"

@app.route("/health")
def health():
    return {"status": "healthy"}

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
EOF

Step 2 — Create requirements.txt

echo "Flask==3.1.0" > requirements.txt

Step 3 — Create the Dockerfile (no extension)

cat > Dockerfile <<'EOF'
FROM python:3.12-slim
WORKDIR /app
RUN apt-get update && \
    apt-get install -y bash procps curl && \
    rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 5000
CMD ["python", "app.py"]
EOF

The apt-get line installs bash, procps and curl so that Lab 3 can open a shell and run ps aux inside the container.

Step 4 — Build the image

docker build -t myapp:v1 .

Step 5 — Verify the image

docker images

Expected: myapp with tag v1 is listed.

Step 6 — Add a second version tag

docker tag myapp:v1 myapp:1.0
docker images

Expected: myapp:v1 and myapp:1.0 share the same IMAGE ID.

Step 7 — Run the container with port mapping

docker run -d --name myapp-container -p 5000:5000 myapp:v1

Step 8 — Test from the host

curl http://localhost:5000
curl http://localhost:5000/health

Expected: Hello from the CCAI Docker Lab! and {"status":"healthy"}. A browser at http://localhost:5000 shows the same text.

Cleanup

docker rm -f myapp-container

Lab 3 — Docker debugging and troubleshooting

Goal: read logs, follow them live, open a shell inside a running container, then break the app on purpose and diagnose it from outside with docker logs and docker inspect. This lab runs on the Lab 2 app, so Steps 1 and 2 rebuild it from scratch.

Step 0 — Install Docker (fresh machine)

sudo apt-get update
sudo apt-get install -y docker.io
sudo systemctl enable --now docker
sudo usermod -aG docker $USER
newgrp docker
docker --version

Step 1 — Create the Lab 2 app files

mkdir -p ~/lab3 && cd ~/lab3

cat > app.py <<'EOF'
from flask import Flask

app = Flask(__name__)

@app.route("/")
def home():
    return "Hello from the CCAI Docker Lab!"

@app.route("/health")
def health():
    return {"status": "healthy"}

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
EOF

echo "Flask==3.1.0" > requirements.txt

cat > Dockerfile <<'EOF'
FROM python:3.12-slim
WORKDIR /app
RUN apt-get update && \
    apt-get install -y bash procps curl && \
    rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 5000
CMD ["python", "app.py"]
EOF

Step 2 — Build and run the Lab 2 container

docker build -t myapp:v1 .
docker run -d --name myapp-container -p 5000:5000 myapp:v1

Step 3 — Confirm the container is running

docker ps

Step 4 — View the container logs

docker logs myapp-container

Expected: Flask startup lines such as Running on http://0.0.0.0:5000.

Step 5 — Follow the logs in real time

Terminal 1:

docker logs -f myapp-container

Terminal 2:

curl http://localhost:5000

Expected: each request appears in terminal 1 as a GET / HTTP/1.1 200 line. Press Ctrl+C in terminal 1 to stop following.

Step 6 — Open a shell inside the running container

docker exec -it myapp-container /bin/bash

Then, inside the container:

pwd
ls
ps aux
exit

Expected: /app, then Dockerfile app.py requirements.txt, then a process list that includes python app.py.

Step 7 — Change app.py to require an environment variable

Back on the host, in ~/lab3:

cat > app.py <<'EOF'
import os
from flask import Flask

app = Flask(__name__)

APP_MESSAGE = os.environ["APP_MESSAGE"]

@app.route("/")
def home():
    return APP_MESSAGE

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
EOF

os.environ["APP_MESSAGE"] raises a KeyError when the variable is not set. That is the deliberate failure.

Step 8 — Build the deliberately broken image

docker build -t myapp:broken .

Step 9 — Run it without the required variable

docker run --name broken-app myapp:broken

Expected: a traceback ending in KeyError: 'APP_MESSAGE', and the container exits.

Step 10 — Inspect the stopped container

docker ps -a

Expected: broken-app with status Exited (1).

Step 11 — Diagnose with logs

docker logs broken-app

Step 12 — Read the exit code with docker inspect

docker inspect broken-app --format='{{.State.ExitCode}}'
docker inspect broken-app --format='{{.State.Error}}'

Expected: 1, then an empty line (the failure was inside the app, not in Docker itself). Exit code 0 means success; anything else means failure.

Step 13 — Run it correctly with the variable supplied

docker run -d --name fixed-app -e APP_MESSAGE="Application is working again" -p 5001:5000 myapp:broken
curl http://localhost:5001

The host port is 5001 because 5000 is still used by myapp-container.

Expected: Application is working again.

Cleanup

docker rm -f myapp-container broken-app fixed-app

Lab 4 — Persistent storage with Docker volumes

Goal: run PostgreSQL 15 with a named volume, create a table with rows, delete the container, start a new one on the same volume and show the data survived.

Step 0 — Install Docker (fresh machine)

sudo apt-get update
sudo apt-get install -y docker.io
sudo systemctl enable --now docker
sudo usermod -aG docker $USER
newgrp docker
docker --version

Step 1 — Create a named volume

docker volume create postgres_data
docker volume ls

Step 2 — Run PostgreSQL 15 with the volume attached

docker run -d --name lab-postgres \
  -e POSTGRES_PASSWORD=admin123 \
  -e POSTGRES_DB=labdb \
  -v postgres_data:/var/lib/postgresql/data \
  -p 5432:5432 \
  postgres:15

The first run pulls the image. Wait 5–10 seconds until docker logs lab-postgres ends with database system is ready to accept connections, or the next step fails with a connection error.

Step 3 — Connect with psql inside the container

docker exec -it lab-postgres psql -U postgres -d labdb

If the lab wants a client on the host instead: sudo apt-get install -y postgresql-client, then psql -h localhost -U postgres -d labdb (password admin123).

Step 4 — Create a table and insert rows

At the labdb=# prompt:

CREATE TABLE students (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100),
  department VARCHAR(100)
);

INSERT INTO students (name, department) VALUES
('Aryaman', 'CSE'),
('Rahul', 'AI'),
('Priya', 'Data Science');

SELECT * FROM students;
\q

Expected: the SELECT shows 3 rows.

Step 5 — Stop and remove the container

docker stop lab-postgres
docker rm lab-postgres
docker ps -a

Step 6 — Verify the volume still exists

docker volume ls

Expected: postgres_data is still listed although the container is gone.

Step 7 — Recreate the container on the same volume

docker run -d --name lab-postgres \
  -e POSTGRES_PASSWORD=admin123 \
  -e POSTGRES_DB=labdb \
  -v postgres_data:/var/lib/postgresql/data \
  -p 5432:5432 \
  postgres:15

Postgres only applies POSTGRES_PASSWORD and POSTGRES_DB when the data directory is empty. Here it already holds your data, so those values are ignored.

Step 8 — Verify the old data survived

Wait a few seconds, then:

docker exec -it lab-postgres psql -U postgres -d labdb
SELECT * FROM students;
\q

Expected: the same 3 rows, which shows the volume kept the data. One-liner version: docker exec lab-postgres psql -U postgres -d labdb -c "SELECT * FROM students;".

Cleanup

docker rm -f lab-postgres
docker volume rm postgres_data

Lab 5 — Docker networking with a custom bridge network

Goal: show that containers on a custom bridge network reach each other by name, and that a container on the default bridge cannot reach them.

Step 0 — Install Docker (fresh machine)

sudo apt-get update
sudo apt-get install -y docker.io
sudo systemctl enable --now docker
sudo usermod -aG docker $USER
newgrp docker
docker --version

Step 1 — Create the custom bridge network

docker network create lab-network
docker network ls

Expected: lab-network appears with driver bridge next to the default bridge, host and none.

Step 2 — Run an nginx web container on the custom network

docker run -d --name web --network lab-network nginx

Step 3 — Run an Alpine client container on the same network

docker run -dit --name client --network lab-network alpine

-dit (detached, interactive, with a terminal) keeps Alpine running in the background. Without it Alpine would exit at once.

Step 4 — From the client, reach nginx by container name

docker exec -it client sh

Inside the container:

ping -c 3 web
wget -qO- http://web
exit

Expected: web resolves to an IP address and replies, and wget prints the nginx welcome page HTML. Docker's built-in DNS resolves container names on user-defined networks.

Optional: docker network inspect lab-network lists both containers.

Step 5 — Run a third container on the default bridge network

docker run -dit --name outsider alpine

Step 6 — Try to reach the custom-network container from the outsider

docker exec -it outsider sh

Inside the container:

ping -c 3 web
wget -qO- http://web
exit

Expected: ping: bad address 'web' and wget: bad address 'web'. The outsider is not on lab-network, and the default bridge has no name resolution. Reaching web by IP address fails too, because Docker isolates the two networks.

Cleanup

docker rm -f web client outsider
docker network rm lab-network

Lab 6 — Multi-container app with Docker Compose

Goal: define a web service and a database in one docker-compose.yml, start them together, read one service's logs, open a shell in a service and tear everything down.

Step 0 — Install Docker and the Compose plugin (fresh machine)

sudo apt-get update
sudo apt-get install -y docker.io docker-compose-v2
sudo systemctl enable --now docker
sudo usermod -aG docker $USER
newgrp docker
docker --version
docker compose version

docker compose (with a space) is Compose v2, installed as a Docker plugin. If the docker-compose-v2 package isn't found, install Docker with curl -fsSL https://get.docker.com | sudo sh instead of docker.io; that script includes the plugin.

Step 1 — Create the project: app, requirements and Dockerfile

The web service builds from a Dockerfile (build: .), so this folder needs the Lab 2 Dockerfile and requirements.txt plus a simple app.py.

mkdir -p ~/myapp-compose && cd ~/myapp-compose

cat > app.py <<'EOF'
from flask import Flask

app = Flask(__name__)

@app.route("/")
def home():
    return "Docker Compose application is running!"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
EOF

echo "Flask==3.1.0" > requirements.txt

cat > Dockerfile <<'EOF'
FROM python:3.12-slim
WORKDIR /app
RUN apt-get update && \
    apt-get install -y bash procps curl && \
    rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 5000
CMD ["python", "app.py"]
EOF

Step 2 — Create docker-compose.yml

cat > docker-compose.yml <<'EOF'
services:
  web:
    build: .
    ports:
      - "5000:5000"
    depends_on:
      - database

  database:
    image: postgres:15
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: admin123
      POSTGRES_DB: labdb
    volumes:
      - compose_db_data:/var/lib/postgresql/data

volumes:
  compose_db_data:
EOF

depends_on makes Compose start database before web. It waits for the container to start, not for Postgres to be ready. compose_db_data is a named volume that keeps the database files.

Step 3 — Start the stack

docker compose up -d

The first run builds the web image and pulls postgres:15, so it takes a minute.

Step 4 — Verify both services are running

docker compose ps

Expected: web and database both listed as running.

Step 5 — Test the web service

curl http://localhost:5000

Expected: Docker Compose application is running!

Step 6 — View and follow the web service logs

docker compose logs web
docker compose logs -f web

Press Ctrl+C to stop following. Run curl http://localhost:5000 in a second terminal to see requests appear.

Step 7 — Inspect the running web service

docker compose exec web /bin/sh

Inside the container:

ls
exit

Expected: Dockerfile app.py docker-compose.yml requirements.txt, because COPY . . copied the whole folder into the image.

Step 8 — Bring the stack down

docker compose down
docker compose ps

Expected: docker compose ps shows an empty list.

Step 9 — Verify the containers and network are gone

docker ps -a
docker network ls
docker volume ls

Expected: both containers and the Compose network (myapp-compose_default) are gone. The named volume (myapp-compose_compose_db_data) is still listed, because down keeps volumes unless you add -v.

Cleanup

docker compose down -v

Lab 7 — Kubernetes Pods with Minikube

Goal: start a local Kubernetes cluster with Minikube, create an nginx Pod from a YAML manifest, inspect it, then delete it and see that nothing recreates it.

Step 0 — Install Docker (fresh machine)

Minikube runs the cluster inside a Docker container (the docker driver), so Docker comes first.

sudo apt-get update
sudo apt-get install -y docker.io
sudo systemctl enable --now docker
sudo usermod -aG docker $USER
newgrp docker
docker --version

Step 1 — Install kubectl

curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
rm kubectl
kubectl version --client

Step 2 — Install Minikube

curl -LO https://github.com/kubernetes/minikube/releases/latest/download/minikube-linux-amd64
sudo install minikube-linux-amd64 /usr/local/bin/minikube
rm minikube-linux-amd64
minikube version

These are the x86-64 builds, which fit the lab PCs. On an ARM machine, replace amd64 with arm64 in both steps.

Step 3 — Start the cluster

minikube start --driver=docker

Run it as your normal user, not with sudo; Minikube refuses the Docker driver as root. The first start downloads images and takes a few minutes.

Expected: the output ends with Done! kubectl is now configured to use "minikube" cluster.

Step 4 — Verify cluster health

kubectl cluster-info
kubectl get nodes

Expected: the control plane and CoreDNS URLs, and a node named minikube with status Ready.

Step 5 — Create the Pod manifest pod.yaml

cat > pod.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
spec:
  containers:
  - name: nginx
    image: nginx:latest
    ports:
    - containerPort: 80
EOF

The four top-level fields to remember: apiVersion (v1 for a Pod), kind (Pod), metadata (name and labels), spec (the list of containers).

Step 6 — Create the Pod

kubectl apply -f pod.yaml

Step 7 — Verify the Pod reaches Running

kubectl get pods
kubectl get pods -w

Expected: nginx-pod goes from ContainerCreating to Running with READY 1/1. Press Ctrl+C to leave watch mode.

Step 8 — Inspect the Pod and read its Events

kubectl describe pod nginx-pod

Expected: the Events section at the bottom shows Scheduled, Pulling, Pulled, Created and Started.

Step 9 — Delete the Pod

kubectl delete pod nginx-pod
kubectl get pods

Expected: No resources found in default namespace. A bare Pod has no controller managing it, so nothing recreates it. A Deployment (Lab 8) does.

Cleanup

minikube stop

minikube delete removes the cluster completely.

Lab 8 — Kubernetes Deployments and scaling

Goal: run the Lab 2 image as a Deployment with 2 replicas, scale it to 5, watch the controller replace a deleted Pod, and scale back to 2. The Deployment needs the myapp:v1 image from Lab 2, so Steps 4 to 6 rebuild it and load it into Minikube.

Step 0 — Install Docker (fresh machine)

sudo apt-get update
sudo apt-get install -y docker.io
sudo systemctl enable --now docker
sudo usermod -aG docker $USER
newgrp docker
docker --version

Step 1 — Install kubectl

curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
rm kubectl
kubectl version --client

Step 2 — Install Minikube

curl -LO https://github.com/kubernetes/minikube/releases/latest/download/minikube-linux-amd64
sudo install minikube-linux-amd64 /usr/local/bin/minikube
rm minikube-linux-amd64
minikube version

On an ARM machine, replace amd64 with arm64 in Steps 1 and 2.

Step 3 — Start the cluster

minikube start --driver=docker
kubectl get nodes

Run it as your normal user, not with sudo.

Step 4 — Create the Lab 2 app files

mkdir -p ~/lab8 && cd ~/lab8

cat > app.py <<'EOF'
from flask import Flask

app = Flask(__name__)

@app.route("/")
def home():
    return "Hello from the CCAI Docker Lab!"

@app.route("/health")
def health():
    return {"status": "healthy"}

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
EOF

echo "Flask==3.1.0" > requirements.txt

cat > Dockerfile <<'EOF'
FROM python:3.12-slim
WORKDIR /app
RUN apt-get update && \
    apt-get install -y bash procps curl && \
    rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 5000
CMD ["python", "app.py"]
EOF

Step 5 — Build myapp:v1 locally

docker build -t myapp:v1 .
docker images

Step 6 — Load the image into Minikube

minikube image load myapp:v1
minikube image ls | grep myapp

The Minikube cluster has its own image store, separate from your host Docker. Without this step the Pods can't find myapp:v1.

Step 7 — Create deployment.yaml

cat > deployment.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-deployment
spec:
  replicas: 2
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
      - name: myapp
        image: myapp:v1
        imagePullPolicy: Never
        ports:
        - containerPort: 5000
EOF

selector.matchLabels must match template.metadata.labels; that is how the Deployment finds its Pods. imagePullPolicy: Never tells Kubernetes to use the image already loaded in Minikube and never pull from a registry.

Step 8 — Apply the Deployment

kubectl apply -f deployment.yaml

Step 9 — Verify the Deployment and its two Pods

kubectl get deployments
kubectl get pods

Expected: myapp-deployment shows READY 2/2, and two Pods are Running.

Step 10 — Scale to five replicas

kubectl scale deployment myapp-deployment --replicas=5
kubectl get pods -w

Press Ctrl+C once all five show Running.

Step 11 — Check the rollout status

kubectl rollout status deployment/myapp-deployment

Expected: deployment "myapp-deployment" successfully rolled out.

Step 12 — Delete one Pod manually

kubectl get pods
kubectl delete pod <POD_NAME>
kubectl get pods

Replace <POD_NAME> with a name copied from the list. To skip the copying: kubectl delete $(kubectl get pods -o name | head -1).

Expected: a replacement Pod with a very young AGE appears at once, so the count stays at 5. That is the Deployment controller keeping the desired state.

Step 13 — Scale back to two replicas

kubectl scale deployment myapp-deployment --replicas=2
kubectl get pods

Expected: the extra Pods show Terminating and then disappear, leaving 2 Running.

Cleanup

kubectl delete -f deployment.yaml
minikube stop

Open-ended 1 — Exposing an app with a NodePort Service

Goal: expose the Lab 8 Deployment with a NodePort Service, reach it from outside the cluster, break the Service by pointing its selector at a label no Pod has, then fix it. This builds on Lab 8, so Steps 4 and 5 recreate the image and the Deployment.

Step 0 — Install Docker (fresh machine)

sudo apt-get update
sudo apt-get install -y docker.io
sudo systemctl enable --now docker
sudo usermod -aG docker $USER

Step 5 — Create and apply the Lab 8 Deployment

cat > deployment.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-deployment
spec:
  replicas: 2
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:

    spec:
      containers:
      - name: myapp
        image: myapp:v1
        imagePullPolicy: Never
        ports:
        - containerPort: 5000
EOF

kubectl apply -f deployment.yaml
kubectl get pods

Expected: two Pods, Running within a few seconds.

Step 6 — Create the Service manifest service.yaml

cat > service.yaml <<'EOF'
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
spec:
  type: NodePort
  selector:
    app: myapp
  ports:
  - port: 5000
    targetPort: 5000
EOF

selector must match the Pod label app: myapp from the Deployment. port is the Service's own port, targetPort is the container port. With no nodePort given, Kubernetes assigns one from 30000 to 32767.

Step 7 — Apply the Service and inspect the assigned NodePort

kubectl apply -f service.yaml
kubectl get svc myapp-service
kubectl get endpoints myapp-service

Expected: the PORT(S) column reads like 5000:31234/TCP, where 31234 is the NodePort. The endpoints list shows two Pod IPs on port 5000.

Step 8 — Access the app from outside the cluster

NODE_IP=$(minikube ip)
NODE_PORT=$(kubectl get svc myapp-service -o jsonpath='{.spec.ports[0].nodePort}')
echo "$NODE_IP:$NODE_PORT"
curl http://$NODE_IP:$NODE_PORT
curl http://$NODE_IP:$NODE_PORT/health

Expected: Hello from the CCAI Docker Lab! and {"status":"healthy"}. The two variables only exist in this terminal. If the node IP isn't reachable (Docker driver on Windows or macOS), run minikube service myapp-service --url and curl the URL it prints.

Step 9 — Point the selector at a label no Pod has

sed -i 's/app: myapp/app: wrongapp/' service.yaml
kubectl apply -f service.yaml
kubectl get endpoints myapp-service
curl --max-time 5 http://$NODE_IP:$NODE_PORT

Expected: ENDPOINTS shows <none> and curl fails (connection refused or timeout). The Pods are healthy, but the Service selects none of them, so no traffic is routed. You can also edit service.yaml in nano instead of using sed.

Step 10 — Correct the selector and confirm access is back

sed -i 's/app: wrongapp/app: myapp/' service.yaml
kubectl apply -f service.yaml
kubectl get endpoints myapp-service
curl http://$NODE_IP:$NODE_PORT

Expected: two endpoints again and the greeting is returned on the same NodePort.

Cleanup

kubectl delete -f service.yaml -f deployment.yaml
minikube stop

Open-ended 2 — ConfigMap, rolling updates and debugging

Goal: feed configuration to a Deployment from a ConfigMap, roll out a new image version, break the rollout with a bad image tag, diagnose ImagePullBackOff, roll back, then check the ConfigMap values, logs and events. This builds on Lab 8, so the app, image and Deployment are recreated here.

Step 0 — Install Docker (fresh machine)

sudo apt-get update
sudo apt-get install -y docker.io
sudo systemctl enable --now docker
sudo usermod -aG docker $USER
newgrp docker
docker --version

Step 1 — Install kubectl

curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
rm kubectl
kubectl version --client

Step 2 — Install Minikube

curl -LO https://github.com/kubernetes/minikube/releases/latest/download/minikube-linux-amd64
sudo install minikube-linux-amd64 /usr/local/bin/minikube
rm minikube-linux-amd64
minikube version

Step 3 — Start the cluster

minikube start --driver=docker
kubectl get nodes

Step 4 — Create the app (it reads its message from an environment variable)

mkdir -p ~/oe2 && cd ~/oe2

cat > app.py <<'EOF'
import os
from flask import Flask

app = Flask(__name__)

APP_MESSAGE = os.environ.get("APP_MESSAGE", "no message set")
VERSION = "v1"

@app.route("/")
def home():
    return f"{APP_MESSAGE} | version: {VERSION}"

@app.route("/health")
def health():
    return {"status": "healthy"}

if __name__ == "__main__":
    print(f"Starting app {VERSION} with message: {APP_MESSAGE}", flush=True)
    app.run(host="0.0.0.0", port=5000)
EOF

echo "Flask==3.1.0" > requirements.txt

cat > Dockerfile <<'EOF'
FROM python:3.12-slim
WORKDIR /app
RUN apt-get update && \
    apt-get install -y bash procps curl && \
    rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 5000
CMD ["python", "app.py"]
EOF

Step 5 — Build myapp:v1 and load it into Minikube

docker build -t myapp:v1 .
minikube image load myapp:v1

Step 6 — Create the ConfigMap

cat > configmap.yaml <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: myapp-config
data:
  APP_MESSAGE: "Hello from ConfigMap"
  APP_ENV: "lab"
EOF

kubectl apply -f configmap.yaml
kubectl get configmap myapp-config

Step 7 — Create a Deployment that loads the ConfigMap as environment variables

cat > deployment.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-deployment
spec:
  replicas: 2
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
      - name: myapp
        image: myapp:v1
        ports:
        - containerPort: 5000
        envFrom:
        - configMapRef:
            name: myapp-config
EOF

kubectl apply -f deployment.yaml
kubectl rollout status deployment/myapp-deployment
kubectl get pods

envFrom.configMapRef turns every key in the ConfigMap into an environment variable in the container.

This file leaves out imagePullPolicy: Never on purpose. A tag other than latest defaults to IfNotPresent, so the image you loaded is used. A tag that doesn't exist then makes Kubernetes try Docker Hub and fail with ImagePullBackOff, which is the error Step 9 needs. With Never you would see ErrImageNeverPull instead.

Step 8 — Rolling update to a new image version

sed -i 's/VERSION = "v1"/VERSION = "v2"/' app.py
docker build -t myapp:v2 .
minikube image load myapp:v2

sed -i 's/image: myapp:v1/image: myapp:v2/' deployment.yaml
kubectl apply -f deployment.yaml
kubectl rollout status deployment/myapp-deployment
kubectl get pods
kubectl rollout history deployment/myapp-deployment

Expected: rollout status reports the old replicas being replaced and ends with successfully rolled out. The Pods have new names and young ages, and the history lists revisions 1 and 2.

Step 9 — Break it with a bad image tag

sed -i 's/image: myapp:v2/image: myapp:v99/' deployment.yaml
kubectl apply -f deployment.yaml
kubectl rollout status deployment/myapp-deployment --timeout=30s
kubectl get pods

Expected: rollout status keeps waiting and then times out, which is the stall. get pods shows two old Pods still Running and one new Pod in ErrImagePull or ImagePullBackOff. The old Pods stay up because a rolling update won't remove them until a new Pod is ready.

Step 10 — Diagnose the failure

BAD_POD=$(kubectl get pods --no-headers | awk '$3!="Running"{print $1; exit}')
kubectl describe pod $BAD_POD

Expected: the Events section shows Failed to pull image "myapp:v99", ErrImagePull, Back-off pulling image and ImagePullBackOff. The cause is that tag v99 doesn't exist.

Step 11 — Roll back to the previous working version

kubectl rollout undo deployment/myapp-deployment
kubectl rollout status deployment/myapp-deployment
kubectl get pods
kubectl get deployment myapp-deployment -o jsonpath='{.spec.template.spec.containers[0].image}' && echo

Expected: successfully rolled out, all Pods Running, and the image prints as myapp:v2. To keep the file in step with the cluster: sed -i 's/image: myapp:v99/image: myapp:v2/' deployment.yaml.

Step 12 — Check the ConfigMap values inside a Pod

POD=$(kubectl get pods -l app=myapp --no-headers | awk '$3=="Running"{print $1; exit}')
kubectl exec -it $POD -- /bin/bash

Inside the Pod:

printenv APP_MESSAGE APP_ENV
exit

Expected: Hello from ConfigMap and lab.

Step 13 — Read the logs and the event history

kubectl logs $POD
kubectl get events --sort-by=.metadata.creationTimestamp

Expected: the logs show Starting app v2 with message: Hello from ConfigMap plus request lines. The events show the whole story: Scheduled, Pulled, Created and Started for good Pods, Failed and BackOff for the v99 Pod, and ScalingReplicaSet lines for the update and the rollback. Kubernetes drops events after about an hour.

Cleanup

kubectl delete -f deployment.yaml -f configmap.yaml
minikube stop

Exam-day gotchas and cleanup

Most lab failures come from leftovers of the previous lab or from not waiting long enough. Check this table before debugging anything else.

SymptomFix
permission denied ... /var/run/docker.sockRun newgrp docker, log out and back in, or prefix the command with sudo.
port is already allocated (5000, 5001, 5432, 8080)docker ps to find the old container, then docker rm -f <name>.
container name "/x" is already in usedocker rm -f x, then run the command again.
psql connection refused, or the database system is starting upWait 5 to 10 seconds and check docker logs lab-postgres.
docker: 'compose' is not a docker commandInstall the plugin: sudo apt-get install -y docker-compose-v2. The hyphenated docker-compose is the old v1 tool.
minikube start refuses to run as rootRun it as your normal user without sudo; that user must be in the docker group.
kubectl says the connection to the server was refusedThe cluster is stopped. Run minikube start.
Pod status ErrImageNeverPullThe image isn't inside Minikube. Run minikube image load myapp:v1.
Pod status ImagePullBackOffThe image tag doesn't exist. Fix the tag, or run kubectl rollout undo deployment/<name>.
docker logs -f, docker compose logs -f or kubectl get pods -w never returnsThat is follow mode. Press Ctrl+C.
NodePort address not reachable from the hostRun minikube service <service-name> --url and use the URL it prints.

Reset everything between labs

docker ps -aq | xargs -r docker rm -f
docker network prune -f
docker volume prune -a -f
minikube delete

This removes every container, every unused network and volume (database data included) and the whole Minikube cluster. Skip minikube delete if you haven't installed Minikube.
